## Overview

June on Practical AI was about the engineering around models. Three founders described tools that take the pain out of deployment, distributed training and similarity search. In a hosts-only episode, Chris Benson and Daniel Whitenack talked about how people and organisations learn their way into AI.

## Main themes

### From notebook to production

- Tuhin Srivastava argues the hard part of machine learning is making a model practical: an API, business logic and users who give feedback. He sums up the problem as “Code is great. Infra is hard” ([BaseTen](/podcasts/practical-ai/2021/06/the-fastest-way-to-build-ml-powered-apps/)).
- He says everyone starts by pickling models, which breaks down as models grow. BaseTen deploys a model with a couple of lines of code and adds a serverless framework for logic on top ([BaseTen](/podcasts/practical-ai/2021/06/the-fastest-way-to-build-ml-powered-apps/)).
- Srivastava says hiring has shifted from data scientists to machine learning engineers, who are very hard to find. He expects pre-trained models such as those on Hugging Face to widen the user base ([BaseTen](/podcasts/practical-ai/2021/06/the-fastest-way-to-build-ml-powered-apps/)).

### Scaling training without rewriting code

- William Falcon says code fails to work across teams largely because hardware code is mixed with model code. Lightning separates the two by factoring out the trainer ([PyTorch Lightning](/podcasts/practical-ai/2021/06/multi-gpu-training-is-hard-without-pytorch-lightning/)).
- He says the bigger benefit beyond multi-GPU training is collaboration and reproducible, scalable code. About 3,000 open-source projects use Lightning ([PyTorch Lightning](/podcasts/practical-ai/2021/06/multi-gpu-training-is-hard-without-pytorch-lightning/)).
- Grid AI handles the cloud GPUs that Lightning alone cannot provide. Falcon says “today, Grid doesn't support deployments” and that its community tier charges only for AWS compute ([PyTorch Lightning](/podcasts/practical-ai/2021/06/multi-gpu-training-is-hard-without-pytorch-lightning/)).

### Vector databases and embeddings

- Edo Liberty says hand-crafted features gave way to learned embeddings, now the lingua franca for images, text, user behaviour and network threats ([Pinecone](/podcasts/practical-ai/2021/06/vector-databases-for-machine-learning/)).
- He started Pinecone because no database existed for storing and retrieving high-dimensional vectors. It runs in memory and trades some accuracy for speed in similarity search ([Pinecone](/podcasts/practical-ai/2021/06/vector-databases-for-machine-learning/)).
- Liberty cites feed ranking at Facebook and LinkedIn, semantic search with BERT models from Hugging Face, fraud detection and recommendation as use cases ([Pinecone](/podcasts/practical-ai/2021/06/vector-databases-for-machine-learning/)).

### Learning AI and organising teams

- Benson argues people must build lifelong learning into their process or fall behind, and recommends a personally significant use case as a way in. The hosts highlight Radek Osmulski's book Meta Learning ([Learning to learn](/podcasts/practical-ai/2021/06/learning-to-learn-deep-learning/)).
- Whitenack weighs centralised AI teams, which must deliberately reach users, against distributed ones, which risk duplicated work. Benson sees AI rolling back into data science and DevOps ([Learning to learn](/podcasts/practical-ai/2021/06/learning-to-learn-deep-learning/)).
- On MLOps, Whitenack notes that courses and enterprises use quite different stacks, and Benson advises learning the concepts rather than one ecosystem ([Learning to learn](/podcasts/practical-ai/2021/06/learning-to-learn-deep-learning/), [BaseTen](/podcasts/practical-ai/2021/06/the-fastest-way-to-build-ml-powered-apps/)).
