## Overview

January paired two very different ways of building software. Mai-Lan Tomsen Bukovec explained how AWS keeps S3 correct at enormous scale by assuming failure and proving correctness. Peter Steinberger, founder of PSPDFKit and creator of Clawdbot (now OpenClaw), described shipping code he does not read by steering many coding agents at once.

## Main themes

### S3: built on the assumption that servers fail

- Tomsen Bukovec says S3 manages “tens of millions of hard drives across millions of servers” in 120 availability zones across 38 regions, holding over 500 trillion objects ([S3](/podcasts/pragmatic-engineer/2026/01/how-aws-s3-is-built/)).
- She calls correlated failure the main threat to availability. S3 stores each object several times across fault domains, so a copy survives if a whole availability zone, rack or server fails ([S3](/podcasts/pragmatic-engineer/2026/01/how-aws-s3-is-built/)).
- Auditor systems inspect every byte across the fleet and trigger repairs, so the team can report actual durability for any week, month or year ([S3](/podcasts/pragmatic-engineer/2026/01/how-aws-s3-is-built/)).

### Proving correctness and adding primitives

- S3 launched in 2006 as eventually consistent. Moving to strong consistency took a replicated journal and a cache coherency protocol, and she says AWS chose not to pass the hardware cost on to customers ([S3](/podcasts/pragmatic-engineer/2026/01/how-aws-s3-is-built/)).
- Every check-in to the index subsystem is automatically proved with formal methods so the consistency model does not regress. She argues that at a certain scale maths has to save you, because no one can test every edge case ([S3](/podcasts/pragmatic-engineer/2026/01/how-aws-s3-is-built/)).
- S3 Tables builds on objects, but S3 Vectors is a new data structure. Vector neighbourhoods are computed ahead of time, giving sub-100 ms warm queries with up to 2 billion vectors per index ([S3](/podcasts/pragmatic-engineer/2026/01/how-aws-s3-is-built/)).

### One engineer, many agents

- Steinberger rejects the term vibe coding and calls his work agentic engineering. His main rule is to close the loop: agents must be able to compile, test and check their own output, which he says pushes him towards more verifiable architecture ([Clawd creator](/podcasts/pragmatic-engineer/2026/01/the-creator-of-clawd-i-ship-code-i-dont-read/)).
- He runs five to ten agents in parallel to stay in flow and finds it more mentally taxing than writing code. He prefers Codex for complex codebases because it reads far more code before writing, and says a multi-provider change took it about three hours against two weeks by hand ([Clawd creator](/podcasts/pragmatic-engineer/2026/01/the-creator-of-clawd-i-ship-code-i-dont-read/)).
- He treats pull requests as prompt requests: “I read the prompts more than I read the code.” He rewrites most contributions with his agent ([Clawd creator](/podcasts/pragmatic-engineer/2026/01/the-creator-of-clawd-i-ship-code-i-dont-read/)).
- Clawdbot began as a WhatsApp relay to his computer and grew from about 100 to 3,300 GitHub stars in a week. Orosz cautions that this is an experimental project and that review would matter more in production systems ([Clawd creator](/podcasts/pragmatic-engineer/2026/01/the-creator-of-clawd-i-ship-code-i-dont-read/)).
